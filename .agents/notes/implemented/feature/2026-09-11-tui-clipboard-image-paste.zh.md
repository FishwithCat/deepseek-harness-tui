# Agent Note: TUI 剪贴板图片粘贴

Status: implemented

[English](2026-09-11-tui-clipboard-image-paste.md) | 中文

## 问题

[本 fork 的终端界面](../architecture/2026-09-11-fork-terminal-surface.zh.md)此前只组合并发送文本：提示无法携带图片，对话记录也没有展示图片的方式。其他每个界面都已接受图片——浏览器输入框支持粘贴与拖放，ACP 与 MCP 会把图片投影为持久块——因此终端用户只能先在别的界面开会话才能附上图片。图片也恰好是终端本身无法送达的一类富输入：括号粘贴只承载文本，没有任何终端转义序列会把图片字节交给全屏应用。

## 决策

**Ctrl+V 把系统剪贴板中的图片附到草稿上。** 应用调用平台自带的剪贴板读取器（`src/clipboard.ts`）：macOS 用 `osascript`，Windows 与 WSL 用经 PowerShell 调用的 `System.Windows.Forms.Clipboard`，Wayland 用 `wl-paste`，X11 用 `xclip`。读取器把字节暂存到系统临时目录下的一个临时文件，无论其中是否有图片，读取都会删除它。Windows 终端与 WSL 会把 Ctrl+V 分发给自身的粘贴，因此该界面在那里把同一动作绑定到 Alt+V——即参照 Agent 的 `app.clipboard.pasteImage` 默认值。读取器声明的媒体类型只是声明而非权威：准入会对照解码后的字节校验，因此标注错误的读取结果会以无效图片失败，而不会被持久化。

**输入框用文本标记引用每个已持有的图片。** Ctrl+V 通过编辑器的 `insertTextAtCursor` 在光标处插入 `[Image #1]`，这正是 pi-tui 为剪贴板图片标记记录的 API。标记就是可编辑的普通文本，因此移动或删除标记即移动或删除对应图片，而从未提交的草稿只在内存中持有字节。提交时会移除草稿仍持有的图片所对应的标记，并在草稿并未持有该图片时把标记原样保留为字面文本；输入框的标记永远不会作为提示文本到达模型。

**提交在任何消息存在之前先准入整批图片。** 应用解析精确路由模型声明的输入模态（缺少声明即为能力未知，照常继续），通过 `ctx.attachments.admitPromptContent(…)` 准入整批图片，然后把提示文本与其后按内容顺序排列的已准入图片块作为一条用户消息交给 Agent。这正是其他界面使用的宿主提示路径：图片在所属事件追加之前就已持久提交，因此重放能精确重建模型所见。被拒绝时——没有附件存储、模型排除图片输入或准入失败——应用恢复草稿，而不是发送残缺的提示。

**对话记录渲染由持久内容派生的标记。** 用户行在其文本之前按内容顺序为每个图片块显示一个标记。编号按消息而非按输入框草稿计数，因此恢复的会话无需任何输入框状态即可渲染出同一行。

## 考虑过的替代方案

**像参照 Agent 那样使用原生剪贴板插件。** `@mariozechner/clipboard` 提供 `hasImage()` 与 `getImageBinary()`，并为各平台提供预编译二进制。它落选是因为它并不能删除平台代码：参照 Agent 仍在其旁附带 `wl-paste`、`xclip` 与 WSL 的 PowerShell 兜底，因为该插件在 Linux 上只支持 X11，也无法从 WSL 看到 Windows 剪贴板。为它引入原生依赖、各平台包、它们的发布年龄豁免与第三方声明，换来的行为与本界面仅用 macOS、Windows 与所有 Linux 桌面自带的程序即可达到的行为相同。

**通过转义协议向终端索取剪贴板。** Kitty 的 `OSC 5522` 读取及同类机制可以把剪贴板数据返回给应用。它因覆盖面和管线而落选：只有少数终端实现读取方向，iTerm2、Terminal.app 与 Windows Terminal 都不在其中，而 pi-tui 也没有向应用代码暴露 OSC 响应通道，因此本界面要为一条多数用户用不上的路径自行维护解析器。

**像 Web 界面那样在输入框上方放附件栏。** 在缩略图可行的场合，文本框上方的缩略图是正确的呈现方式。它在终端里落选，是因为附件栏无法编辑：输入框只有一个文本缓冲，单独的附件栏需要自己的移除按键，也需要在引用它的文本之外另立排序规则，而标记可以像其他字符一样用 Backspace 删除。

**像参照 Agent 那样插入平台的暂存文件路径。** 参照 Agent 把剪贴板图片写入临时文件并插入其路径，依赖它自己的「路径转附件」入口。它落选是因为本 harness 对用户提示没有这样的入口：路径会以字符串形式到达模型，图片永远不会成为持久内容块，读取它还得多一次工具调用。

**剪贴板中没有图片时回退为剪贴板文本。** 参照 Agent 用一个按键同时粘贴图片或文本。它落选是因为终端本身已经能送达文本粘贴：该回退需要在每个宿主上再写一个读取器，而且在 macOS 上会把 Ctrl+V 变成 Cmd+V 之外的第二个文本粘贴键。

## 后果

终端用户现在可以把截图粘贴进提示，并在对话记录中看到该提示携带了哪些图片；这些图片与其他界面共用同一个持久附件存储，因此恢复的会话会保留它们。代价是每个宿主各需一个平台读取器、粘贴依赖平台工具存在（两者皆无的宿主会报告剪贴板为空），以及一条新的运行时依赖边：`dsh-tui-app` 现在声明 `@deepseek-ai/dsh-attachment`，以读取它所准入的存储。

## 测试

`tests/clipboard.spec.ts` 通过注入的命令运行器驱动每条读取器路径——已提供媒体类型之间的优先顺序、读取器缺失与非零退出、空载荷、两种脚本语言的路径加引号，以及 WSL 的路径转换——并用真实文件系统检验实际的暂存文件适配器。`tests/images.spec.ts` 固定标记折叠。`tests/tui-app.spec.ts` 挂载真实的 `dsh-attachment-local` 存储，证明一次 Ctrl+V 粘贴会以文本加持久图片块到达 Agent，纯图片提示在没有文本时也能提交，剪贴板无图片、纯文本路由与附件存储缺失三种情况都会报告并恢复草稿，在 Ctrl+V 被占用的宿主上由 Alt+V 生效，以及 kitty 协议的一对按下/释放事件只触发一次粘贴。`tests/transcript.spec.ts` 固定持久图片提示渲染出的行，包括恢复后的纯图片提示。随附 profile 的一次伪终端运行确认了输入框提示、真实剪贴板读取，以及此后输入框显示的标记。

已指明的覆盖缺口不变：本包拥有一个终端，因此无密钥快照框架无法录制本界面。`tests/clipboard.spec.ts` 替换命令运行器并断言每个读取器传入的参数，因此只有 macOS 读取器经过真实剪贴板的端到端验证（一张真实 PNG，随后被本地存储准入）；其他平台的真实读取仍是手工检查。

# Agent Note: TUI 恢复会话时重建已存储的对话

Status: implemented

[English](2026-09-18-tui-resume-history.md) | 中文

## Problem

终端界面在创建或恢复 Agent 之后只订阅实时的 `session/event` 日志，而恢复会话中较早的事件是被种入 Session 的，不会重新发布。因此执行 `dsh --resume <session-id>` 或在输入框执行 `/resume` 的用户会面对一份空的对话记录：模型仍持有整段对话，但屏幕只显示恢复之后发生的内容。姊妹笔记加入的退出提示让 id 容易打印，却也把一份看起来像新会话的对话记录交给了用户。

## Decision

**恢复会话会把已存储的事件在接受输入之前折叠进对话记录。** `TuiApp.attach()` 检测到带种子的 Session（`session.firstLiveSeq > 0`）后，通过新增的 `TuiSession.history()` 读回已存储的前缀，并把每个事件按实时事件相同的方式应用到 `Transcript`。

**读取走持久化后端，而不是已弃用的内存快照。** `TuiSession.history()` 用 `ctx.sessionPersistence.open(id, 'read')` 打开会话并读取 `[0, firstLiveSeq)`。这样改动就落在[同步读取弃用决定](../architecture/2026-09-09-deprecate-synchronous-session-event-reads.zh.md)所要求的显式异步读取路径上；对话记录属于按需呈现的历史内容，需要的是已存储记录而非投影状态。

**读取在 `firstLiveSeq` 处停止。** 恢复之后追加的事件序列号大于或等于该边界，会通过实时的 `session/event` 订阅到达应用，因此绝不会被折叠两次。

**读取期间到达的事件先缓冲。** 订阅在读取开始前装好；读取进行中时，`session/event` 监听器把事件追加到缓冲区而不是对话记录。缓冲区在已存储行之后应用，因此即使某个 turn 在历史尚未加载完时启动，日志顺序也能保持。

**`mount()` 会等待这次重建。** `TuiApp.boot()` 等待 `mount()`，`/resume` 的 `replaceSession()` 在报告切换之前等待 `attach()`，因此恢复之后的通知会追加在已恢复的行之后，而不是之前。

## Alternatives considered

**在生产代码里调用 `session.snapshotEvents()`。** 它只需一次同步调用、无需后端读取，但它正是同步读取弃用决定禁止新生产代码使用的那次调用；而且对话记录本来读的就是历史记录而非投影状态，对应决定中明确允许的异步读取场景。

**先重建再订阅，而不缓冲。** 这样在读取期间启动的 turn 会因为尚未装好实时订阅而丢失事件，而 `/resume` 可能恢复一个会立即行动的目标或逾期日程。缓冲只多一个数组和一个标志。

**只在用户滚动时按需折叠。** 渐进加载能限制每次读取的规模，但本界面的对话记录是一份内存中的单一列表，没有由滚动触发的加载器，而用户要的验收结果正是进入时就看到已恢复的对话。

## Consequences

恢复的会话现在看起来就是它本来的对话：提示、回复、工具行与通知都会回来。重建会再读一次已存储日志（恢复路径已经读过一次），并在读取完成后一次性折叠，因此很长的会话会在输入框出现前多付一次后端读取。部署没有挂载持久化后端时无法恢复历史；这种部署本来也无法恢复会话，`history()` 会返回空。

## Testing

`tests/tui-app.spec.ts` 在一个桩持久化后端之上分别以 `--resume` 和 `/resume` 启动，断言已存储的提示与回复进入对话记录、在历史读取期间落地的实时事件应用在已存储行之后，以及后端拒绝读取时会产生一条对话记录通知。由于本界面没有录制会话快照，验收由包内测试承担。
